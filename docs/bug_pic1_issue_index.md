## 3. 问题登记

### BPI-001：FANCA 用药知识未完成迁移

- 严重度：`P1`
- 状态：`已实现规则与回归；部署前待报告组确认医学措辞`
- 图证：IMG-353。
- 当前事实：
  - `panels/crc_358_msi/rules/reviewed_part3_knowledge.yaml` 现已同时包含 FANCA `gene_sections` 与限定性 `drug_sections`。
  - 基础基因知识库只在“基因变异解析”sheet 收录 FANCA，用药提示解析 sheet 无 FANCA。
  - 靶向药物候选库有两条 FANCA–Olaparib CGI 泛化记录，但属于无具体位点的 `MUT/CNA`、Case report 证据。
  - 生产过滤要求公共库条目有位点，并要求 CGI 证据等级至少达到 Late trials；上述两条会被正确过滤，不能直接放宽门槛上线。
  - 当前合成 FANCA Ⅱ类移码病例：第三部分生成 FANCA 基因简介、变异解析和限定性用药段；普通错义与Ⅲ类反例不生成该用药结论。
- 根因：FANCA 的“基因层知识”已迁移，“药物层知识/审核规则”未迁移或未获批准；不是单纯 Excel 行漏读。
- 验收条件：
  1. 报告组明确 FANCA 功能缺失型变异的适用范围、药物、证据等级、癌种边界和来源。
  2. 以 Panel reviewed override 或 reviewed drug section 落地，不降低全局位点/证据过滤标准。
  3. 合成 FANCA LoF 与 FANCA 普通错义两个反例测试，证明只命中获批范围。
  4. 同时核对 Part 2 药物相关计数、摘要表和 Part 3 用药解析。

### BPI-004：第三部分编号样式和层级错误

- 严重度：`P1`
- 状态：`已修复并经 FANCA DOCX 视觉复测`
- 图证：IMG-358、IMG-359。
- 根因线索：
  - 动态插入阶段曾直接使用 `num_id=9`。
  - 后处理寻找十进制编号时只检查 level text “包含 `%1`”，因此 `[ %1 ]` 一类定义也可能被误认为 `1.`。
  - level 1 可以缺失，导致子标题无法稳定得到 `2.1`，出现第二个 `[2]`。
- 验收条件：一级严格为 `1.`、`2.`，二级严格为 `2.1`、`2.2`；Word、WPS、LibreOffice 三端一致，并检查 XML 的 numId/ilvl/lvlText。

### BPI-006：签名和报告日期被推到下一页

- 严重度：`P2`
- 状态：`已修复为同一不可拆分段落并经视觉复测`

- 根因线索：`_normalize_signature_layout()` 会把原本同一行的报告日期拆成新的右对齐段落，增加垂直高度；当免责声明刚好占满页面时，签名/日期块会整体或部分被推到下一页。

### BPI-007：二维码/公司介绍尾页锚点错位

- 严重度：`P1`
- 状态：`回归确认正常；已纳入页面级视觉复测`

- 根因线索：公司介绍和二维码由 `_apply_report_content_fixes()` 在方法/局限尾部动态插入；模板中又存在原二维码媒体。历史参考文献边界或浮动锚点变化可能把原二维码带到质控页。现有测试只检查二维码存在，没有检查二维码所在页和尾页顺序。
