# CRC358 历史金标准与批量生成加固 Spec

状态：工程发布候选（生产状态以 iyun129 `REVISION` 与发布证据为准；医学二审待完成）
负责人：Codex（工程修复与 AI 一审）
医学终审：报告组二审
适用 Panel：`crc_358_msi`
基线提交：`4545e0b`

## 1. 目标

本 Spec 将报告组指定的历史 CRC358 病例固化为受控金标准，并从根部修复以下六类问题：

1. 批量任务在服务切换、异常退出后的假运行和丢队列；
2. 旧格式 Msisensor 汇总行未被生产解析；
3. 历史终版中的精确位点知识未完整迁移；
4. 小结、2.1、第三部分的筛选和 VAF 排序不一致；
5. 动态表格合并、性别称呼和签名资源链路不完整；
6. 机器 QA 能 PASS、但历史金标准 Diff 仍 FAIL。

完成后，系统必须能够用同一套通用规则生成与历史终版医学内容一致的报告，不允许按患者姓名、样本号或文件名硬编码。

## 2. 隐私与数据边界

- 真实 Excel、历史 Word、真实签名和患者身份信息只允许存在于 `bug_file/`、`.work/` 或生产 `storage/`；不得进入 Git。
- 仓库中只提交脱敏的结构化验收契约、合成测试数据、伪签名和文件 SHA-256。
- 真实历史报告在运行时参考报告库注册，使用外部 `storage/reference_reports/` 和 SQLite 记录；代码库不保存 DOCX 正文。
- 仓库内代号统一为 `crc358_reviewed_case_a`，不得写入真实患者姓名或样本编号。

## 3. 金标准定义

“100% 一致”分为两个层次：

### 3.1 必须精确一致的医学/结构内容

- 原始变异集合、HGVS、变异分级和 VAF；
- 检测结果小结的基因、位点、获益/耐药药物和证据等级；
- 靶向药物备注中的“通用名[商品名]”集合与审核顺序，且只能来自最终展示的
  获益/耐药药物列；
- 2.1 表和第三部分的基因/位点集合；
- 第三部分基因解释和药物解析的条目数量、方向、药物名及正文；
- Word 表格和第三部分共用“基因分组 VAF”契约：基因按本基因
  最高 VAF 降序、同基因内按 VAF 降序、同值保持输入序号；这既保证
  表格行可纵向合并，也保证第三部分基因解析、药物解析与前文顺序一致；
- MSI/TMB、性别称呼、检测/审核签名角色；
- 同基因相邻行的 Word 纵向合并语义。

### 3.2 允许存在的非业务差异

- Word、WPS、macOS/Linux LibreOffice 造成的页码或轻微分页差异；
- DOCX 压缩包顺序、关系 ID、生成时间等二进制差异；
- 已登记且报告组同意不继承的历史空白页或旧版式缺陷。
- 已在脱敏契约 `intentional_deviations` 中逐项登记的其他历史差异；候选件必须
  符合本 Spec 的统一分组排序，且差异在报告组二审前保持可见、不得标为
  已医学确认。

禁止把缺失药物、缺失基因、方向变化、证据等级变化或正文缺段列为可忽略差异。

## 4. 基准病例验收契约

仓库内脱敏契约必须至少断言：

- 小结靶向药物相关行：7 行；
- 靶向药物商品名备注：41 项，集合与顺序必须和历史终版一致；免疫表商品名备注
  独立渲染，不得被靶向药物处理器覆盖；
- 第三部分基因解释：11 节；
- 第三部分药物解析：18 节；
- 第三部分 11 个基因解释必须满足“基因按最高 VAF 降序、同基因位点相邻且
  组内 VAF 降序”，完整顺序以脱敏契约 `part3.gene_section_order` 为准；
  前三项必须为 `APC 22.03% -> APC 17.50% -> SMAD4 20.00%`；
- 精确位点必须覆盖：
  - `TP53 c.499C>T / p.Q167*`；
  - `FLT3 c.2537G>A / p.G846D`；
  - `ATR c.1291delA / p.R431Gfs*8`；
  - `KRAS c.34G>T / p.G12C`；
- 相关变异排序必须为 `KRAS 13.58%`、`DNMT3A 1.18%`、`TP53 1.16%`、`FLT3 1.02%`、`ATR 0.98%`；
- TP53 不得因药物列为空而从小结消失；
- FLT3 不得只出现在小结/2.1 而缺失第三部分药物解析；
- KRAS G12C 必须使用历史 reviewed 位点规则，不得回退到公共候选药物集合；
- 同一基因连续表格行必须存在 OOXML `w:vMerge`；
- 女性合成病例必须渲染“女士”，男性合成病例必须渲染“先生”；
- 缺失签名资源必须产生明确 QA/发布警告，生产发布前签名注册表必须可解析。

## 5. 分步实施

### S1 批量任务生命周期与 MSI

实施：

- 生产进程使用运行时互斥锁，禁止旧/新 uvicorn 同时操作同一 SQLite 与任务队列；
- 发布脚本必须等待旧进程完全退出，超时后明确终止，再启动候选版本；
- 新进程取得互斥锁后再执行未完成任务恢复；
- 批量恢复必须只重排 `pending/running` 子项，保留已完成项，重置被中断项的输出和错误；
- 恢复记录必须可从运维状态接口读取；
- 旧格式 Msisensor 汇总行和 `msisensor2/msisensorpro` 优先级必须有回归测试；
- 当前生产假运行任务在新版启动后必须被恢复或明确终态化。

验收：

- 单元测试模拟进程互斥、重启恢复、批量部分完成后恢复；
- 服务切换后不存在两个相同端口的活动 uvicorn；
- 数据库 `running` 且运行队列 `active=0/queued=0` 的任务不得无限停留；
- 已知旧格式 MSI 工作簿解析为 `MSS`，而不是“未检测”。

### S2 正式金标准注册

实施：

- 新增通用注册/校验脚本，将外部 DOCX 写入现有参考报告库；
- 正式注册必须同时提供版本库内脱敏契约；脚本校验 panel、外部 case ID、参考
  DOCX SHA-256，并拒绝把脱敏 `case_alias` 当成运行时病例编号；
- 注册记录包含 panel、外部 case ID、名称、SHA-256、active 状态和审核备注，并在
  外部存储生成 `.golden.json` 凭据；普通 Web 上传基准不具备正式验收资格；
- 同一 panel/case 仅允许一个 active 基准；
- 新增脱敏契约 `crc358_reviewed_case_a`，用于无 PHI 的 CI/发布断言。

验收：

- 测试数据库可注册、激活、查询并命中参考报告；
- 真实 DOCX 和 Excel 不出现在 `git status` 的可提交清单中；
- 普通自动 Diff 可按 panel + case ID 命中 active 基准；金标准验收模式仅命中通过
  契约、文件哈希和凭据复核的 active 正式金标准。

### S3 精确知识迁移

实施：

- 从历史终版迁移 TP53 Q167*、FLT3 G846D、ATR R431Gfs*8、KRAS G12C 的位点级小结规则、基因解释和药物解析；
- 保留历史正文和来源标识，标记为 `legacy_runtime`，并记录 `pending_report_group_reconfirmation`；
- 规则键至少包含 panel、癌种范围、gene、c.HGVS、p.HGVS、变异方向和证据等级；
- 禁止把上述规则泛化到同基因任意变异。

验收：

- 四个位点正例命中；
- 同基因非目标位点反例不命中；
- 小结、2.1、第三部分药物解析能够对账；
- 知识治理校验无来源、审核状态或运行资格冲突。

### S4 统一筛选与排序

实施：

- 建立一个跨章节共用的稳定排序键：`基因最高 VAF 降序 -> 基因首次输入序号
  -> 同基因 VAF 降序 -> 同值保持原始输入序号`，统一用于小结、2.1、免疫/NCCN、
  第三部分基因解释、药物解析和相应参考文献；
- reviewed overlay 追加完成后必须再次排序；
- 分类筛选与药物命中是两个独立维度：已审核且需展示的变异不得仅因药物为空而静默消失。

验收：

- 表格内部共享聚组顺序一致；第三部分内部的基因解释、药物解析和文献顺序一致；
- 第三部分与前文表格共享分组顺序，APC 两个位点必须相邻，组内满足
  `22.03 >= 17.50`，随后再进入 SMAD4 `20.00`；
- ATR 位于 FLT3 之后；
- 同基因多位点保持相邻，允许 Word 对基因/转录本/染色体列做数据驱动纵向合并；
- 重复运行顺序稳定；
- 第二个病例不残留基准病例位点或药物。

### S5 Word 与运行时资源

实施：

- 对动态变异/药物表执行相邻同基因纵向合并；
- 默认 CRC358 金模板移除硬编码称呼，统一由性别映射生成；
- 签名解析优先使用外部 `RG_WEB_STORAGE_ROOT/signatures`，测试仅用伪签名；
- 金模板的精简处理器链必须显式执行靶向药物商品名汇总，不得沿用模板里的静态
  历史列表；商品名映射和报告组审核顺序分别维护在
  `config/drug_brands.yaml` 的 `brands` 与 `targeted_summary_order`，不得依赖 YAML
  字典顺序；重叠药名必须最长非重叠匹配，禁止把“替西罗莫司”误报成同时命中
  “西罗莫司”；
- 部署 preflight 校验 configured signer 对应文件存在，真实签名不进入 release 目录。

验收：

- OOXML 检查存在预期 `w:vMerge restart/continue`；
- 男女双病例称呼测试通过；
- 有签名资源时两角色均显示，无资源时 QA 明确告警；
- Linux LibreOffice 渲染无新增空白页、孤行标题或签名拆页。
- 靶向商品名备注由当前病例最终药物列动态生成；无匹配药物时显示明确空状态，
  有匹配药物时不得漏项、增项或误改免疫商品名备注。

### S6 发布阻断门禁

实施：

- 将脱敏契约断言加入 `make release-check`；
- 普通生成保持“有基准则比对”；报告组选择“金标准验收”后，每个病例都必须命中
  正式金标准，缺基准、基准凭据失效、候选缺失或 Diff `FAIL` 均阻断交付；
- 发布门禁记录 reference SHA、候选 SHA、Diff 状态、规则/知识哈希，并将“门禁运行
  环境指纹”与“候选报告实际渲染环境指纹”分开记录；
- 候选 QA 必须记录生成源码 revision、干净状态和候选 DOCX SHA；外部 manifest
  必须同时固定 `candidate_source_revision`、`candidate_sha256` 和
  `candidate_qa_sha256`，且三方 revision 与发布 HEAD 完全一致；
- 正式候选只能在 Linux 上执行阻断式全页视觉 QA；QA 必须记录 LibreOffice、
  Poppler、隔离 profile 模式、机器架构及固定 CJK 字体替换表哈希，
  候选 QA、外部 manifest 与生产运行指纹三者必须一致；随后使用
  `scripts/attest_historical_golden_manifest.py` 从 QA 原始证据生成 manifest
  凭据，禁止手工填写哈希或渲染器字段；
- CRC301/358 目录刷新、最终 PAGEREF 缓存构建和样式收口属于关键处理器；生产
  缺少 LibreOffice、python3-uno、Poppler 或启用了 FAST_TOC/skip 开关时必须
  失败关闭，不能降级成“报告生成成功”；
- 至少运行基准病例和第二个差异病例，防止患者特异硬编码。

验收：

- 缺少 TP53、FLT3 药物段、商品名缺项/乱序、排序错误、称呼错误或合并缺失中的
  任意一项都会使门禁失败；
- `make release-check`、panel package validation、相关 pytest、双病例生成和视觉 QA 全部通过；
- iyun129 的 release、`REVISION`、进程 cwd、运行时配置和公开健康检查一致。

## 6. 生产发布与回滚

发布前必须满足：

- 工作树中没有待发布范围外改动；
- 目标提交已冻结并可追溯；
- 生产数据库、上传、报告、签名和参考报告目录已备份；
- 已记录当前 known-good release；
- 本地和 Linux 候选门禁均通过。

发布后必须验证：

1. 运行进程 cwd 与目标 release 一致；
2. `REVISION` 为目标完整 SHA；
3. 启动恢复处理了遗留批量任务；
4. 旧格式 MSI 复测通过；
5. 基准病例生成与 Diff 通过；
6. 公网单份和批量路径均可用。

任何 P0/P1 失败立即切回已记录的 known-good release；运行时数据不得随代码回滚删除。

## 7. 完成判定

只有以下条件同时满足才标记完成：

- S1-S6 的自动测试和人工视觉验收均有证据；
- 历史基准 Diff 无业务类 ERROR；
- 生产 smoke 和批量恢复通过；
- 未提交患者文件、真实签名或密钥；
- 报告组仍保留二次医学审核权，AI 一审不被表述为医学终审。
